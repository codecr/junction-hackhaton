## What we are building

A local agent (Node, on each attendee's machine, as the Events API guide requires: "it has to run locally") that signs the attendee in with their AWS Builder ID, reads and writes only their own schedule via the AWS Events API, and serves the web UI at `127.0.0.1`. Agents exchange **signed manifests** (session IDs and codes, nothing else) with a squad. Every agent runs the same deterministic solver on the same inputs, so all reach the same proposals with no coordinator. A small serverless squad server (API Gateway, Lambda, DynamoDB, deployed with CDK) is the mailbox, used by default; file and paste exchange also works. Amplify Hosting serves the landing page, docs, downloads and a fully client-side demo with fictional data. Browser-side sign-in on the hosted site is not built; it is only an experiment pending written confirmation (ADR-012).

## Rules that never bend

1. **Events API credentials never leave the attendee's machine.** No access token, refresh token or ID token is ever sent to any server of ours, logged, put in an error report, put in a URL, or written anywhere except `~/.junction/` (mode 0600). Browser code never holds tokens: the UI talks to the local agent. Our backend never calls the Events API and never receives an `Authorization` header meant for it. The Events API guide also says tokens in a browser live in memory only; that applies to any experiment.
2. **The squad server stores only signed envelopes, and only these fields.** Session IDs and codes, priorities and holds (session IDs), busy blocks and venue only at the sharing level the member chose, plus the text the squad itself wrote: squad name, member display names, charter topic labels and matching taxonomy labels, and scout notes (140 characters, plain text). Never titles, abstracts, speakers, rooms, emails or tokens. Titles are resolved locally from each member's own catalog. `guardian` checks the server against this exact list.
3. **The re:Invent catalog is not public.** Never commit it. Never derive demo or test data from it. Fixtures are invented and generated by a seeded script. Real captures live in `fixtures/private/` (git-ignored).
4. **The Events API has no idempotency key.** After any bulk write or any `CreatePersonalTime`, reconcile with `GetSchedule` before retrying. Never blind-retry a write. Re-sending `CreatePersonalTime` creates a duplicate.
5. **Bulk operations succeed per session, not per request.** Never report "done" from an HTTP 200. Report the per-session outcome and confirm from `GetSchedule`.
6. **Respect per-attendee quotas** with a per-operation token bucket: GetSession 120/min, ListSessions 60, GetSchedule 60, CancelReservation 30, DisassociateFavorite 30, Create/Update/DeletePersonalTime 30 each, ReserveSessions 30 sessions, AssociateFavorites 30 sessions. On 429 wait `Retry-After`. `409` means the operation is closed (reservations before Oct 8 via API), not a bug.
7. **Paginate until `nextToken` is absent.** A short page is not the last page. Treat every session field as optional.
8. **Junction only touches personal-time entries it created**, identified by a tag in the description (docs/03). Never edit or delete the attendee's own entries.
9. **Never invent Events API fields.** If a field or behaviour is not in `fixtures/` or docs/04 as verified, write a spike, record the result in `docs/FINDINGS.md`, then build on it.
10. **Determinism is a feature.** The solver and the claim rule are pure functions of (charter, manifests, catalog snapshot). No randomness, no clock reads, no locale-dependent sorting. Same inputs, byte-identical outputs on every machine.

## Repo layout (target)

```
packages/core     pure TS: schemas (zod), canonical JSON, signing, code parser, repeat groups, coverage, solver, claim rule, venue graph
packages/agent    Node: OAuth PKCE sign-in on loopback 8484-8489, Events API client + pacer (types from the official OpenAPI), catalog store (node:sqlite), sync, local HTTP server on 127.0.0.1:4848 (serves the web UI), CLI
packages/web      React + Vite UI, plain CSS on design/tokens.css. Served by the agent; demo build with fictional data and no network is hosted on Amplify

packages/relay    Lambda handlers for the squad server
infra             AWS CDK v2 (TypeScript): site, relay, alarms, budget
fixtures          generated demo data (committed) and private captures (ignored)
spikes            throwaway scripts, never imported by packages
docs, design, schemas, .claude
```

## Conventions

- TypeScript strict, ESM, Node 22. Validate every boundary with zod (Events API responses, relay payloads, files pasted by users).
- One reducer-style pure core; side effects only in `agent`, `relay`, `web`.
- Tests with every feature. Property tests (fast-check) for solver determinism, feasibility and monotonic improvement.
- Conventional Commits. Small commits. Never commit generated `dist/` or `cdk.out/`.
- Errors tell the user what happened and what to do. No vague failures, no apologies.

## Design rules (full detail in docs/05-DESIGN.md)

- Use only `design/tokens.css`. No Tailwind, no component library skins, no icon pack. Draw the handful of icons as inline SVG.
- The Marey-style day chart is the one memorable element. Everything around it is quiet.
- Banned: all-caps eyebrow labels, `A · B · C` meta strings, `→` in buttons, numbered markers for non-sequences, gradient washes, identical rounded cards, fade-up on every section, cream backgrounds with terracotta accents, near-black with a neon accent.
- Every member has a colour **and** a marker shape **and** a name. Never colour alone.
- Compare against `design/reference-desktop.png` and `reference-mobile.png` after every UI change (`/design-review`).
